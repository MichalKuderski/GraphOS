Proposed architecture

Build an engineering system whose claims can be checked.

GraphOS should combine a deterministic execution controller, replaceable agent workers, and a graph connecting requirements to artifacts and verification evidence.

The most valuable ambition is consistent delivery across an expanding, explicitly supported set of project types. That requires a reliable way to specify work, choose an appropriate team, preserve state, evaluate results, recover from failures, and recognize when evidence is insufficient. Intelligence is supplied by models; the platform makes their work accountable.

The supplied diagram provides the right high-level pattern: task routing, single-agent or parallel work, shared evidence, independent verification, and targeted repair. This proposal supplies the contracts and operational semantics between those boxes. It also adds specification versioning, integration, external-action reconciliation, resource accounting, and post-release observation.

Central invariant: acceptance is a relationship between a requirement revision, an exact artifact, a verification procedure, and its evidence. A message saying “done” cannot create that relationship by itself.

Graph engineering is a strong fit because dependencies, provenance, authority, and invalidation are relationships. It does not establish that graph-shaped systems are inherently the most intelligent architecture. A graph database is optional; precise graph semantics are essential.

One control system, several kinds of intelligence.

Select a component to inspect its responsibility. Numbered stages describe the main path; repair and revision can return work to earlier stages under explicit limits.

Intent & acceptance

Translate the request into requirements, constraints, assumptions, deliverables, acceptance checks, and action permissions. Preserve the user's goal; record uncertainty rather than silently inventing requirements.

Separate proposal from authority

The planning model can propose tasks, dependencies, tools, and revisions. Controller code decides whether a proposal is valid, affordable, authorized, and schedulable. Workers can submit candidate artifacts. Verification services can submit evidence. Only the acceptance controller can mark a requirement satisfied, and only the release controller can authorize a consequential external effect within the user's established scope.

This separation is not an organizational chart of permanent agents. A “role” is a contract, capability set, context scope, and evaluation profile. A single capable model may perform several compatible roles in sequence. Fresh workers are created where parallelism, context separation, or independent review has measurable value.

The control plane and the execution plane

The control plane owns durable admission, plan versions, state transitions, budgets, and evidence requirements. The execution plane contains disposable model sessions, tool processes, sandboxes, test runners, and domain adapters. An agent crash should discard a worker, not the project's meaning. This is consistent with contemporary architectures that separate session storage, harnesses, and sandboxes. Anthropic's session / harness / sandbox design

The user interface should expose decisions, current artifacts, blocked criteria, costs, and next actions. It should make it possible to answer “Why is this accepted?”, “What changed?”, “What remains uncertain?”, and “What will this action affect?”

Compile a specification into a valid plan

  1. Validate all schemas, reference types, and required identifiers.
  2. Map deliverables to requirements and verification procedures; retain unresolved assumptions explicitly.
  3. Identify dependencies, semantic interface boundaries, and shared write conflicts.
  4. Detect strongly connected components. Reject control loops without an exit condition, deadline, and retry budget.
  5. Check reachability: mandatory work must be able to terminate as accepted, failed, blocked, or cancelled.
  6. Check capabilities and compute a feasible budget envelope, including integration and verification.
  7. Record a versioned plan and input manifest before dispatch.

Dynamic planning remains available through a PlanPatch proposal that follows the same validation process. A plan change creates a new version and invalidates affected work. The planner cannot silently remove failing tests or lower acceptance standards to achieve a success flag.

Content and semantic identity

Hash a canonical manifest containing the requirement revision, input artifact hashes, interface/schema versions, source base commit, policy revision, and relevant environment configuration. Store artifact bytes by content hash. Keep a separate stable logical ID for “the checkout API” across revisions. Byte equality and semantic validity answer different questions.

When a requirement or input changes, traverse dependency edges to mark descendants stale. Keep historical artifacts and evidence, but remove their eligibility to certify the current result. Recompute only the affected region when dependency coverage is trustworthy. Run broader integration checks when dependencies may be missing or a public interface changes.

Formal verification where it pays

Model-check the small controller state machine and critical concurrent transitions. Useful properties include no accepted stale attempt, no oversubscribed reservation, and no release using superseded verification. Temporal-logic liveness assumptions must include eventual infrastructure availability and finite retries. Formal methods can verify those modeled mechanics; they do not prove an arbitrary generated app meets an ambiguous human goal.

Recovery is a protocol, not a retry button.

PROPOSED → READY → CLAIMED → RUNNING → SUBMITTED → VERIFYING → ACCEPTED
                       ↘ RETRY_WAIT                 ↘ REPAIR_REQUIRED
                       ↘ BLOCKED / EFFECT_UNKNOWN

ACCEPTED → STALE when required inputs or acceptance policy change
Any eligible state → CANCEL_REQUESTED → CANCELLED or reconciliation

The production task record needs task_id, plan_version, input_manifest_hash, attempt_id, lease_epoch, state_version, deadline, reserved_cost, and scoped capabilities. Admission is durably recorded before returning an accepted request to the caller.

Claims, leases, and fencing

Claim work in a transaction using compare-and-swap or equivalent serialization. Lease expiry does not mean the old worker stopped. Each new claim receives a higher fencing epoch. Artifact writes, tool dispatch, and completion records must be rejected if their epoch is stale. A worker that wakes after a network partition cannot overwrite a newer worker's result.

Completion and its outgoing notification commit together to the task ledger and transactional outbox. Delivery can repeat; consumers deduplicate by message ID and logical operation ID. The database transition, rather than the order messages happen to arrive, determines authoritative state.

External effects have separate state

PREPARED → AUTHORIZED → DISPATCHED → CONFIRMED
                              ↘ UNKNOWN → RECONCILING
                                          ├→ CONFIRMED
                                          ├→ CONFIRMED_ABSENT
                                          └→ MANUAL_RESOLUTION

Persist a logical operation key, canonical payload hash, authority scope, and target before dispatch. Every retry of that same operation must reuse the same key and payload. A new worker attempt must not create a fresh payment, deployment, or order identity.

If an external service commits an action and its response is lost, the correct local state is unknown. Query authoritative remote state or retry through receiver-enforced idempotency. If neither is available, pause the action for resolution. A local outbox cannot establish exactly-once effects in a remote system.

LangGraph documentation explicitly describes at-least-once node execution and the need for application-level idempotency. Checkpoint durability and external-effect safety are different concerns. Its time-travel feature re-executes downstream work; it does not reverse external reality. Fault tolerance · Checkpointers · Time travel

Cancellation and compensation

Cancellation revokes permission to start new work and asks current workers to stop. It does not erase effects already committed. Reconcile in-flight actions before declaring the run cancelled. A compensating action is another operation with its own permission, outcome, and possible failure; some effects cannot be undone.

Bounded resources

Reserve funds and execution capacity atomically before dispatch. Include model calls, tool calls, verification, failed branches, and retries. Maintain limits for money, tokens, elapsed time, attempts, parallelism, and external actions. Reconcile actual usage and unresolved provider charges before releasing reservations. A worker's voluntary estimate is insufficient to enforce a hard spend ceiling.

Use deadlines, a cancellation token, bounded exponential backoff with jitter, and a provider circuit breaker. Record model fallback as a configuration change because it can change output behavior. Pin workflow versions for paused runs, and migrate or drain incompatible workflows explicitly.

Agents exchange contracts and evidence.

A task handoff contains an objective, required inputs and versions, allowed tools, write scope, output schema, acceptance criteria, budget, deadline, and known uncertainty. Its result contains artifact references, evidence references, unresolved issues, and actual resource use. Free-form messages explain these objects; they do not replace them.

MessageEnvelope
  schema_version · message_id · project_id · run_id · task_id

  kind: command | question | result | evidence | plan_patch | status

The schema in this package is a starting wire contract. Production also requires authenticated sender identity, authorization checks, durable deduplication, bounded payloads, ordering rules, and an explicit schema migration policy. Schema validity cannot prove a claim true or authorize an action.

Communication topology

Use scoped coordinator-to-worker handoffs and artifact publication by default. Allow direct worker consultation only when a named dependency requires it. A disagreement becomes an issue with competing claims, supporting evidence, a decision owner, and a proposed resolving test. Unbounded group debate is neither a termination policy nor an integration strategy.

Split work by context and interfaces, not by creating an agent for every human job title. Good boundaries include an independently testable API module, a separate research branch, or a black-box usability review. Poor boundaries require repeated reconstruction of the same global context.

Instruction boundaries

Keep user-authorized policy and trusted runtime configuration separate from retrieved documents, generated code, websites, attachments, and tool outputs. An external document saying “ignore previous instructions” is content, not a control-plane update. The tool gateway should enforce narrow capabilities, egress rules, and credential access even if the model follows malicious text. Worker sandboxes should not receive release credentials or authority to rewrite their graders.

MCP is useful for tools and context integration; A2A is useful for interoperable agent task exchange. Neither supplies GraphOS's acceptance semantics or universal delivery guarantees. Add them at integration boundaries rather than making internal reliability depend on an assumed protocol guarantee. MCP specification · A2A specification

Independent verification means operational separation

Verify in a clean environment against the submitted artifact, not the builder's workspace. Give the verifier the specification and artifacts without making the builder's narrative its authority. Keep trusted graders and expected outcomes outside worker write access. Test changes can be proposed, but relaxing a mandatory criterion requires a distinct specification decision.

Different model names do not prove independent failure modes. Use executable oracles where available. For subjective design and game enjoyment, use rubrics calibrated against human judgment. Model review can find defects; it cannot certify taste, business value, or universal correctness.

Before trusting a grader, confirm that a reference solution passes and an unchanged or deliberately broken solution fails. Mutation-test critical graders. Protect the test runner, dependency resolution, and environment as well as the test files. A passing result from modified instrumentation is not trusted evidence.

Integration is another production step

Workers receive isolated worktrees or equivalent versioned workspaces. Freeze interface contracts before parallel implementation. Each patch names its base commit. A single integration authority serializes merges, resolves semantic conflicts, and verifies the resulting integration revision. Two locally passing patches can still produce a broken application.

Verification of a feature branch does not automatically certify the merged commit. Reuse evidence only where inputs and environment match the declared scope; run integration checks on the assembled artifact. The release controller rechecks bindings immediately before acting to prevent changes between verification and release.

A repair record includes a fault signature, hypothesis, changed artifact, resulting evidence, and remaining budget. Repetition without a new hypothesis or genuinely transient cause should not consume another unlimited cycle. Spend intelligence where it improves the result.

The router chooses among a small set of validated patterns: direct tool execution, one capable agent, sequential stages, parallel independent workers, generator–verifier, or a bounded combination. It uses task coupling, uncertainty, available graders, consequence of error, context size, and historical performance. Initial rules should be explicit; learn a routing policy only after enough representative data exists.

Novel design exploration can use a small portfolio of contrasting concepts before implementation. Separate novelty, feasibility, quality, and cost in evaluation. Retain genuinely different candidates; ten superficial variants are not a useful search portfolio. The user should be able to select aesthetic or product tradeoffs that automated tests cannot decide.

What a complete GraphOS run looks like.

Example request: build a small analytics application with CSV import, editable filters, a chart, and an export. This is an illustrative workflow, not a claim that this app has been generated.

  1. Specify: define supported file sizes and formats, empty/error states, filter semantics, privacy constraints, export behavior, browser targets, and required user journeys. Unknown choices become explicit assumptions.
  2. Compile: create tasks for data parsing, API/storage if required, UI, and integration. Define one shared data contract. Associate every required behavior with a grader.
  3. Route: use one builder for tightly coupled work, or two workers for independent parsing and UI surfaces if the contract is stable and the budget supports integration.
  4. Execute: each worker consumes exact input revisions, works in its sandbox, and submits artifacts and evidence. Workers cannot mark themselves accepted.
  5. Integrate: assemble one candidate commit. Detect API mismatches even when separate branch tests passed.
  6. Verify: a clean browser journey imports a representative file, changes filters, checks the rendered data, exports it, and confirms expected values. Accessibility and failure-state checks use declared criteria.
  7. Repair: if export ignores a filter, attach that failure to the requirement and candidate hash; repair the affected module and rerun its dependent checks.
  8. Deliver: produce the application, reproducible build instructions, acceptance report, limitations, and preview artifact. Production release uses the scoped action policy.
  9. Observe: later defects attach to the released manifest and become regression cases. Candidate lessons enter evaluation before changing future behavior.

If the user changes “CSV” to “CSV and Excel” during verification, the specification version changes. GraphOS identifies affected parsers, UI validation, export assumptions, and tests. Unaffected design work may be reused, but the old acceptance certificate cannot certify the new requirement.

If the integrator crashes after an artifact upload, its deterministic operation identity permits recovery. If a deployment succeeds but the response is lost, GraphOS queries deployment state rather than launching an untracked second release.

Distinguish pass@k, at least one success among k attempts, from pass^k, success across all k attempts. For a task with c successful runs among n, the combinatorial estimator for all-k success is C(c,k)/C(n,k), under the relevant repeated-trial assumptions. Do not raise an aggregate completion rate to the kth power and call it a reliability estimate. Use task- or repository-clustered uncertainty. τ-bench · Agent evaluation guidance

Promotion policy

Predeclare whether a change aims for higher completion, lower cost at comparable quality, or lower latency. An example policy is a positive lower confidence bound for paired completion improvement with no critical regression; an efficiency policy could require noninferiority within a selected margin plus a material cost reduction. Those margins are engineering choices. A small pilot may be inconclusive, which should trigger more measurement rather than a superiority claim.

Fault-injection gate

  • Kill a worker after an external effect succeeds but before acknowledgement is recorded.
  • Resume an expired worker after a replacement has claimed the same task.
  • Change an input, test suite, or candidate after verification begins.
  • Deliver duplicate, delayed, malformed, and out-of-order messages.
  • Integrate two locally valid but semantically incompatible patches.
  • Exhaust a shared budget while several workers request reservations.
  • Restart the controller before its first checkpoint and during a paused workflow upgrade.
  • Inject instructions into retrieved material that attempt to change policy or expose secrets.
  • Cancel while an action is in flight, and verify reconciliation before final status.

Zero observed failures is not proof of zero risk. With zero failures in n independent representative trials, a rough 95% upper failure-rate bound is 3/n. Correlated repeats of a few tasks do not provide the equivalent evidence of thousands of representative trials.

Long-horizon evaluation needs dependent projects, revisions, context loss, and interruptions. Many independent small tasks do not establish multi-day engineering reliability. Definition of a production-capable first version

It supports one declared project family, survives the documented fault suite, enforces budgets and authority outside the model, delivers reproducible artifacts, exposes blocked work honestly, and demonstrates its quality/cost tradeoff against a strong baseline. Universal application coverage is not a first-version acceptance criterion.

Freeze the controller, permissions, and release policy outside autonomous self-modification. Agents may propose improvements as reviewed changes, evaluated on a held-out suite and rolled out gradually. Allowing the optimizer to change its own success criteria would invalidate the experiment.

The defensible differentiator is the integrated system: evidence controls acceptance; dependency graphs control invalidation; measured outcomes control routing; scoped authority controls effects. Its value must be established in working software.

The reference kernel is an in-memory executable specification. It does not implement an LLM agent, database, concurrent scheduler, authentication, sandbox, production queue, real test runner, deployment, or trading execution. Its identities and effect outcomes are supplied by the caller. Budget enforcement assumes declared costs. These limits are documented in its README.

The contracts likewise do not enforce cross-record consistency, authorization, or truthful evidence. The architecture describes how those production services should be built. This package is a concrete starting point and design specification, not a finished universal development system.

Future implementation should first port or wrap the demonstrated invariants in the chosen durable runtime and transactional store, then connect one real builder and verifier. Do not use the small model as a production coordinator merely because its unit tests pass.
